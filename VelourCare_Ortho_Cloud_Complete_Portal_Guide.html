2. Role-Based Access Control (RBAC) & The Complete Permission Matrix

2.1 The Eight System Roles

VelourCare enforces a strict Principle of Least Privilege across eight defined system personas:

  • 1. Super Admin (super-admin): Full global system authority. Manages roles, system configurations, users, audit logs, encrypted backups, and platform parameters.
  • 2. Operations Admin (admin): Coordinates clinics, registers new doctor practices, handles CAD planner and lab allocations, and oversees cross-platform turnaround times.
  • 3. Senior CAD Planner (planner): Evaluates intraoral scans, generates staging files in WaveATP, places composite attachments, sets IPR protocols, and prepares 3D setups for doctor review. Strictly blocked from billing and invoices.
  • 4. Aligner Production Lab (vendor): Receives approved 3D printable STL models. Coordinates resin printing, thermoforming, laser trimming, scallop polishing, laser marking, and courier dispatch. Strictly restricted to assigned manufacturing queue cases.
  • 5. Clinic Doctor / Practice Owner (client): Treats patients, creates cases, reviews and approves treatment plans, downloads step files, tracks shipments, and manages clinic branch invoices.
  • 6. Associate Doctor (see_only_own_uploads: true): Clinical orthodontist practicing within a multi-doctor clinic. Restricted strictly to cases they personally uploaded, preventing exposure of other practitioners' patients.
  • 7. Billing & Accounts (accounts): Generates invoices, applies promo discounts, validates 5% UAE VAT, monitors Stripe payouts, and exports financial ledgers. Strictly prohibited from viewing patient medical histories or clinical records.
  • 8. Unassigned Staff (none): Default quarantine role assigned to new registrations. Has zero permissions (HTTP 403 on all clinical and financial routes) until vetted by an administrator.

3. Multi-Tenant Clinic Isolation, Anti-IDOR Protections & Personal Scoping

3.1 The Tenancy Boundary

In an orthodontic network serving hundreds of independent practices, cross-clinic data leakage is a critical security vulnerability. VelourCare implements a hardware-grade logical boundary ensuring that under no circumstances can Clinic A inspect, enumerate, or tamper with patients, scans, treatment plans, or invoices belonging to Clinic B.

3.2 Anti-IDOR (Insecure Direct Object Reference) Protection

An attacker manipulating a numerical ID in an API call (e.g., requesting GET /api/cases/6 while authenticated as Clinic 1) is immediately intercepted by the tenancy boundary middleware:

[Doctor at Clinic A] ----> GET /api/cases/4 (Belongs to Clinic B) | v +---------------------------------+ | server.js IDOR Guard Layer | | User Client ID: 1 | | Case Client ID: 2 | | Mismatch Detected! | +---------------------------------+ | +------------+------------+ | | v v [Write to Audit Log] [Return HTTP 404] "IDOR_CASE_TAMPERING_BLOCKED" "Case #4 not found." (User, Timestamp, Client IP) (Does NOT return 403 to prevent leakage of ID existence!)
🔒 Strategic Security Choice: Why 404 Instead of 403?
When an IDOR violation occurs, returning HTTP 403 Forbidden confirms to the attacker that the requested resource ID exists. VelourCare strictly returns HTTP 404 Not Found, eliminating identifier enumeration and reconnaissance.

3.3 Associate Doctor Personal Upload Scoping

In large multi-specialty dental centers, associate doctors frequently need isolation from other doctors within the same practice. VelourCare provides two complementary scoping mechanisms:

1. Profile-Level Strict Scoping (see_only_own_uploads: true)

When an associate doctor profile has see_only_own_uploads: true enabled:

  • The cases listing endpoint (GET /api/cases) filters results strictly to records where created_by === user.id, uploader_id === user.id, or doctor_id === user.id.
  • Direct detail retrieval (GET /api/cases/:id) validates personal ownership. If an associate doctor attempts to open another colleague's case from the same clinic, the request is blocked with a 404 Not Found.
  • Status capsule counters display counts calculated solely from their personal caseload.

2. On-Demand Filtering (filters[my_cases_only]=true)

Practice owners and head orthodontists who normally possess clinic-wide visibility can toggle the "My Cases Only" filter at will. The query engine immediately restricts the view to their personal uploads without altering their administrative permissions.

5.2 Status Capsule Count Preservation Logic

A common bug in modern Single Page Applications occurs when status capsule counts (e.g., "Newly Created: 3", "In Planning: 7") drop to zero whenever a specific filter is clicked.

// High-Reliability Architecture in server.js: // 1. Establish tenant boundary and personal scoping FIRST: const baseAccessibleCases = [...cases]; // 2. Pre-calculate capsule counts BEFORE any filter clipping: const getCount = (st) => baseAccessibleCases.filter(c => c.status.value === st).length; const statusCapsules = [ { value: null, label: "All Cases", count: baseAccessibleCases.length }, { value: "newly-created", label: "Newly Created", count: getCount("newly-created") }, { value: "in-planning", label: "In Planning", count: getCount("in-planning") }, { value: "review-treatment-plan", label: "Review Treatment Plan", count: getCount("review-treatment-plan") }, { value: "plan-approved", label: "Plan Approved", count: getCount("plan-approved") }, { value: "in-manufacturing", label: "In Manufacturing", count: getCount("in-manufacturing") }, { value: "completed", label: "Completed", count: getCount("completed") } ]; // 3. Apply search, category, and status filters ONLY to the table page data: cases = applyFilters(cases, params);

This ensures that when a clinician clicks the "Review Treatment Plan" tab, the table filters to show only those cases while the remaining capsule badges proudly maintain accurate counts of all other stages.

6. Digital CAD Planning Studio & 3D Lab Production Queue

6.1 WaveATP & Smile Inspector Integration

VelourCare integrates directly with specialized orthodontic planning suites. Planners import raw .STL and .PLY intraoral dental scans, segment crowns, assign roots based on panoramic X-rays/CBCTs, and compute precise aligner sequences.

  • Smile Inspector: Browser-accessible 3D WebGL viewer allowing doctors to inspect tooth movement animations step-by-step, occlusal contacts, collision maps, and superimpositions (initial vs final).
  • WaveATP Connector: Automated staging algorithms calculating velocities (maximum 0.25mm translational movement and 2° rotational movement per aligner stage) to safeguard periodontal ligament health.

6.2 Signed Short-Lived Download Tokens for 3D Assets

Intraoral dental scans and patient dental models represent sensitive Protected Health Information (PHI). They must never reside in publicly accessible S3 buckets or static URLs without authentication.

1. Client requests step files: GET /api/files/signed-download-token?case_id=1&filename=step-01.stl 2. Backend verifies active session and tenancy ownership. 3. Backend generates cryptographically signed HMAC token with 15-minute expiration: { "download_url": "/api/files/download/step-01.stl?token=5f3d9b1c7a4e8d2e&expires=1731945600", "expires_in_seconds": 900 } 4. Direct asset access without a valid, unexpired token returns HTTP 401 Unauthorized.

7.3 Invoice Immutability & Concurrency Control

⚠️ Financial Integrity Rule: Issued Invoices are Locked
Once an invoice is transitioned to sent, issued, or paid, it is permanently locked against modification or deletion (returning HTTP 400 Bad Request). Any financial adjustment must be handled via formal credit notes or supplementary invoices. Furthermore, optimistic concurrency locking on updated_at timestamps prevents race conditions and accidental double-charges.

8. Enterprise Security, Threat Mitigation, Cryptography & Rate Limiting

8.1 Password Security & Cryptographic Salting

VelourCare never stores plain-text passwords. All credentials are hashed using PBKDF2 over SHA-512 with 100,000 iterations and a cryptographically unique 32-character hexadecimal salt generated via crypto.randomBytes(16) per account.

8.2 Brute-Force Lockout Defense

The authentication gateway continuously tracks failed login attempts indexed by IP address and username:

  • Threshold: 5 consecutive failed login attempts within a 15-minute window.
  • Action: The IP address and user account are placed in automated lockout. Subsequent attempts immediately return HTTP 429 Too Many Requests with a clear warning: "Too many failed login attempts. Account temporarily locked for 15 minutes."
  • Uniform Error Messaging: To prevent username enumeration, both an invalid username and an invalid password return the identical response: "Invalid username or password."

8.3 HTTP Response Headers & Data Protection Stack

HTTP Header Configured Value Security Protection
X-Content-Type-Options nosniff Prevents MIME-type sniffing and malicious file execution.
X-Frame-Options SAMEORIGIN Guards against Clickjacking attacks and iframe embeds by third parties.
Strict-Transport-Security max-age=31536000; includeSubDomains Enforces strict HTTPS connections for 1 full year.
Content-Security-Policy default-src 'self' ... Prevents malicious script injection and untrusted CDN execution.
Referrer-Policy strict-origin-when-cross-origin Prevents leakage of sensitive URL path tokens to external domains.

8.4 Input Sanitization & Information Leakage Prevention

  • XSS Prevention: All incoming JSON payloads, chat messages, and clinical notes are sanitized to neutralize <script> tags and malicious HTML event attributes.
  • SQL / NoSQL Injection Immunity: Parameterized object filtering and strict type parsing ensure injection payloads are treated as inert string literals.
  • Suppressed Stack Traces: In production mode, unexpected server errors return sanitized JSON ({ error: "Internal Server Error", code: 500 }). Raw Node.js stack traces, database schemas, and filesystem paths are never leaked to the client.

9. Operational Continuity, Automated Backups & Immutable Audit Trails

9.1 Immutable Audit Log Architecture

Every clinical access event, plan approval, IDOR blocking, invoice generation, user deactivation, and backup restoration is recorded in an immutable ledger (db.auditLogs). Super Admins can query these logs via GET /api/audit-logs.

AUDIT LOG ENTRY STRUCTURE: { "id": 142, "user_id": 2, "user_name": "Dr. Alexander Wright, DDS, MS", "role": "client", "action": "APPROVE_TREATMENT_PLAN", "resource_type": "case", "resource_id": 1, "details": "Doctor approved clear aligner plan for case VELOUR-0001", "ip_address": "192.168.1.104", "timestamp": "2026-10-24T14:15:00.000Z" }

9.2 Automated & On-Demand Backup Engine

The VelourCare operational engine incorporates an automated backup and restoration subsystem managed via POST /api/backups/create and POST /api/backups/restore.

  • Full Database Snapshots: Captures complete states of cases, treatment plans, step files, invoices, users, and audit logs.
  • Integrity Hashing: Every backup archive generates a cryptographic SHA-256 integrity checksum upon creation.
  • Integrity Verification: Prior to executing a restoration, the backup runner validates the checksum. If any tampering or byte corruption is detected, the restore aborts immediately, safeguarding the active cluster.

9.3 Soft-Archive Case Deletion Protocol

In healthcare systems, hard database deletions are dangerous and non-compliant with medical records retention regulations.

📋 Soft-Archive Policy
When an administrator deletes a case (DELETE /api/cases/:id), the system flags the record with is_archived: true and deleted_at: timestamp. The case is instantly hidden from standard UI views, searches, and doctor pipelines (returning 404 Not Found), while preserving complete audit provenance and medical records for legal compliance.
